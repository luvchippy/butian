# 报告模板与过审技巧

## 为什么报告重要

同一个漏洞，写得好的给高危 3000，写得差的判低危 100 或不收。

审核员一天看几百份报告。**你的报告要在 30 秒内让他明白：这洞是真的、有危害、能复现。**

## 标准结构（六段，缺一不可）

```markdown
# 【等级】系统名 + 漏洞类型 + 影响后果

## 1. 漏洞信息
| 项 | 内容 |
|---|---|
| 影响域名 | https://xxx.target.com |
| 漏洞类型 | 未授权访问 |
| 危害等级 | 高风险 |
| 是否需登录 | 否 |
| 复现难度 | 低（浏览器直接访问）|

## 2. 复现步骤
（编号写，每步一个动作，贴完整请求/响应）

## 3. 影响范围与危害
（能拿到什么数据、多少量、能干什么）

## 4. 修复建议
（具体到中间件/参数级别）

## 5. 佐证材料
（截图，敏感打码）

## 6. 补充说明
（测试边界：只读、未修改任何数据、测试账号xxx）
```

## 三条提分技巧

1. **等级自己先定，并给出理由**。你写「高风险」并解释为什么是高风险，审核倾向跟着你走。
2. **证明危害链条，别只证明单点**。「能读到用户列表」是低危，「能读到含手机号/身份证的 10 万条用户列表且可翻页遍历」是高危。
3. **主动声明测试边界**。写上「本次测试仅做读取验证，未下载、未修改、未留存任何业务数据」，审核通过率明显更高。

## 降级/被拒的救法

| 情况 | 应对 |
|---|---|
| 判「无危害」 | 补充危害链证明（数据敏感性、可批量性），申诉 |
| 判「重复」 | 认，换目标。别争 |
| 判「需登录」 | 用两个账号做越权证明，重新提交 |
| 判「环境问题」 | 确认是不是测试环境，是就放弃 |
| 长时间无响应 | 7 天后催审，附漏洞仍然存活的证明 |

## 存档规范

每个提交都存一份：

```
reports/
└── 2026-10-30-target-未授权访问用户列表.md
    ├── 截图1-请求.png
    ├── 截图2-响应.png
    └── 截图3-资产范围.png
```

**资产范围截图一定要存**。万一以后有争议，这是你唯一的护身符。
